## IP 互联网协议 - 网络地址转换
主机 DNS 都需要IP 而且路由器一个端口就要一个IP
为了解决IP不够用的问题（当然NAT也带来了其他例如安全性的好处），产生了 **网络地址转换 NAT**

对于外界而言，本地网络中的所有设备共享一个IPv4地址

所有离开本地网络的数据报具有一个相同的源地址NAT（统一计划为路由器的地址），但是具有不同的端口号

例如数据报的源和目的地址为10.0.0/24 则还有8位留给不同的主机，例如10.0.0.1 10.0.0.2...一共32-24=8 即最多$2^8-2$个主机（-2因为10.0.0.255是广播，10.0.0.0指代网段）

本地网络中的所有设备都有一个只能在本地网络中使用的“私有”IP地址空间中的32位地址

**一个公网 IP 下 NAT 最多维持 约60000(2^16) 条外向连接**

**优点:**
所有设备只需要一个IP地址
可以在不通知外界的情况下更改本地网络中的主机地址
可以在不改变本地网络设备地址的情况下更换ISP
安全性: 局域网内的设备不能直接寻址，外部世界不可以直接看到

如果 NAT 用端口来区分不同的主机，那主机内的服务（进程）又是怎么区分的？端口还能区分吗？
有两个“端口层面”：外网端口（路由器端口） 和 内网端口（主机端口）

**实现: NAT 路由器必须具备的能力**
外出数据报: 替换 (source IP address, port #) 为 (NAT IP address, new port #)
远端的 clients/servers 将会用 (NAT IP address, new port #) 作为目的地址

在 NAT 转换表维护每个(source IP address, port #) 和 (NAT IP address, new port #) 转换对 （WAN/LAN）

到来数据报: 替换到来数据报 (NAT IP address, new port #) 为NAT转换表中对应的(source IP address, port #)

隐含的意思是，路由器需要改包头，修改IP和checkSum

e.g 主机 10.0.0.1 发送数据报到 128.119.40.186, 80
NAT 路由器更改数据报源地址、端口号从10.0.0.1, 3345 到 138.76.29.7, 5001,并更新转换表中对应表项
收到回应, 目的地址: 138.76.29.7, 5001
路由器变换目的地址从138.76.29.7, 5001 到10.0.0.1, 3345 

NAT 使用“公网端口号”作为标签（tag），
来唯一标识一个（内网主机IP + 内网进程端口）组合

**NAT 争议:**
路由器本应该只处理到第三层（NAT是网络层 传输层，因此router需要改报文）
地址短缺可以被IPv6解决
违反端到端原则(端口号会被网络层设备修改)
NAT 穿越: 如果客户端要连接NAT路由器后的服务器（客户端需要连接地址为10.0.0.1的服务器
服务器地址10.0.0.1是LAN本地地址，在WAN找不到，整网只有一个外部可见地址）

NAT穿越的解决方案：
**方案1.静态配置NAT**
转发进来的对服务器特定端口连接请求 即固定一个映射

**方案2.UPnP(Universal Plug and Play) IGD(Internet Gateway Device)协议**
即主机获知网络的公共IP，之后修改路由器上的端口映射

**方案3.中继** （加一个公网上的服务器）
NAT后面的服务器建立和中继的连接
外部的客户端链接到中继
中继在2个连接之间桥接

**方案4.用UDP打洞**
中继，其实就是告诉客户端自己的公网的IP
A 和 B 都主动向 S 发 UDP 包，迫使 NAT 给双方建立可互相到达的 NAT 映射

## IPv6
128bit IP地址
40-byte 固定头部长度
支持对“流”进行不同的网络层处理

**数据报格式**
priority: 标记优先级
flow label: 标记流
128bit的地址（不需要头长度标记，因为头长度固定）
移除checksum（加快router处理速度）
没有分片 没有optional部分(放到了next header部分，标记了可能传输层、链路层的信息)

**从IPv4到IPv6**
很多路由器还不支持IPv6
隧道（Tunneling）: IPv6数据报作为IPv4数据报的有效载荷在IPv4路由器之间传输(“packet within a packet”)

外面套的IPv4的头，实际上指向的地址并不是目的地，而是一个同时支持IPv4和IPv6的双栈路由器，它会拆包之后发送IPv6包到目的地

## 泛化转发 SDN
传统互联网的分布式使得维护和升级涉及所有设备，还是太困难了
因此，有人提出网络控制平面可以采用集中的处理方式

**SDN Software defined network**
实现一个remote controller

网络设备数据平面和控制平面分离
数据平面-分组交换机
将路由器、交换机和目前大多数网络设备的功能进一步抽象成：按照流表（由控制平面设置的控制逻辑）进行PDU（帧、分组）的动作（包括转发、丢弃、拷贝、泛洪、阻塞）
统一化设备功能：SDN交换机（分组交换机），执行控制逻辑
控制平面-控制器+网络应用
分离、集中
计算和下发控制逻辑：流表

SDN 交换机在收到一个数据包后，如果不知道目标 MAC 地址，就需要通过 ARP 协议来获得目标主机的 MAC 地址，或者将 ARP 请求上送给控制器处理

**匹配+动作**
每个路由器都有一张转发表（alias flow table流表）
包括“匹配+动作（match plus action）”：匹配到达报文中的字段，采取动作；还有stats（计数器）

SDN 的交换机更强：可以看很多字段
它可以匹配链路层、网络层、传输层的头部字段：

|层级	|可匹配字段例子|
|-|-|
二层|	MAC 地址、VLAN ID
三层|	源/目的 IP、协议号
四层|	源/目的端口号（TCP/UDP）


**泛化转发:** （不是基于目的地的转发）
许多头部字段可以决定动作
有许多可选的动作: drop/copy/modify/log packet

流: 由头部字段所定义 (链路层、网络层、传输层的字段)
**一组具有“相同头部字段模式（pattern）”的数据包即为流**
泛化转发: 简单的分组处理逻辑
匹配: 分组头部字段的模式（pattern）值
动作: 对于匹配的分组: 丢弃、转发、修改、将匹配的分组发送给控制器
优先级: 几个模式匹配了，优先采用哪个，消除歧义
计数器: #bytes 以及 #packets

**openflow** 控制器给交换机下指令的协议
例如实现基于目的地的转发、防火墙...

可以用这种思路理解传统的网络设备：
路由器
match: 固定为最长前缀匹配IP目的地址
action: 固定为通过一条链路转发
交换机
match: 固定为目的MAC地址
action: 固定为转发或者泛洪

进一步，我们可以通过编排好的表去构造网络行为

## 中间盒
在源主机和目的主机之间的数据路径上，除IP路由器的一般标准功能外，执行其他功能的任何中间设备

NAT
application-specific: CDN
Firewalls(看字段) IDS(入侵检测系统，看payload)
Load balancers: 数据中心，企业etc
Caches...

现在，中间盒逐渐从封闭硬件走向开放API的白盒硬件发展，支持match+action的可编程本地动作
网络功能虚拟化(network functions virtualization NFV)就是基于百合网络、计算、存储的可编程服务

**IP沙漏模型**
Internet 细腰结构: 
一个网络层协议: IP 必须在每一台(数十亿)连接Internet的设备上实现
即：应用层 传输层 链路层 物理层都有很多协议；而网络层仅有IP协议（当然现代发展出了中间盒NAT NFV caching Firewalls）

有关端到端：一些网络功能(例如，可靠数据传输、拥塞控制)可以在网络中或在网络边缘实现，因此智能、计算、大规模基建应该在边缘
